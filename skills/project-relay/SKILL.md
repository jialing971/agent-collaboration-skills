# 开发接力

运行环境：本技能的所有命令仅支持 Windows，包含本地状态与交接命令。

唯一代码源在本 Skill 目录。两端共享同一实际项目目录的 `协作记录/state.sqlite3`；`handoff --brief` 返回实际派活使用的有限上下文，完整 `handoff` 保留全部检查点和证据供人工追溯。切换工具不需要重放内部对话。

## 入口

根据本技能文件的位置定位 `scripts/relay.ps1`，使用 `-Project '实际项目根目录' <命令>`。PowerShell 入口优先使用环境变量 `PROJECT_RELAY_PYTHON` 指定的 Python 可执行文件；未配置时使用当前用户的 Codex bundled Python。缺失时请用户配置 Python 3.10+ 的绝对路径，不修改系统 PATH。也可用已确认的 Python 直接运行 `scripts/relay.py --project '项目目录' <命令>`。

命令相对本 Skill 目录解析；不要把文档里的“项目目录”作为实际路径。

## 开始或接回

1. 运行 `status`。若尚未初始化，运行 `init`。结合已有 `shared-project-memory` 读取项目历史，核对实际分支和文件。
2. 对已有任务运行 `handoff --task <ID> --brief`，读取任务身份、当前计划、最近检查点与审核意见、最近执行结果和审核起点。该输出就是 `run` 实际发送的有限上下文；需要人工追溯全部事件、多份检查点和原始 stdout 时改用不带 `--brief` 的完整 `handoff`。任务绑定创建时的分支；当前分支与任务分支不一致时 `handoff` 会拒绝，先切回原分支。运行 `takeover --task <ID> --agent codex` 或 `--agent claude` 明确接管。仍有执行进程时等待其结束，不绕过占用。
3. 用户有新目标时，在 `协作记录/<问题名>/` 写明目标、允许修改范围、验收与测试命令。用 `new --title '问题名' --plan-file '计划绝对路径'` 建任务。`new` 初始负责人为 Codex；Claude 独立建任务后立即接管。

## Codex 在线时派活

Codex 完成需求澄清和计划后，先 `doctor` 核对 CC Switch 路由，再 `run --task <ID> --timeout 900 --max-turns 20`。这是启动真实 Claude Code，按用户现有 DeepSeek 接入计费。执行器使用本机文件和命令工具，工作目录是指定项目；它不是操作系统安全沙箱。

`run` 自动使用与 `handoff --brief` 相同的有限上下文：任务身份与完整计划（上限 12000 字符）、最近一个检查点（3000）、最近一条 Codex 审核/返工意见（3000）、最近执行的 ok/error/结束时间与证据路径（错误 500）、审核起点/当前分支和改动概况（1000），不含历史 events、stdout/stderr、tool payload 或 live JSONL。整体序列化上限 20000 字符；计划或总预算超限时在启动执行器、创建批次或改变任务状态之前拒绝，不静默截断验收条件，也不调用模型做摘要。`brief` 返回实际字符数和限额，不是精确 token 数。

默认配置位于当前用户目录的 `.project-relay/config.json`，也可在子命令之前传 `--config '配置绝对路径'`。配置只存执行器路径、预期路由和凭据来源文件的位置。使用者按本技能目录中的 `config.example.json` 创建自己的配置。未配置 `cc_switch_db` 时，启动读取现有桌面配置中的网关凭据；配置该项后，每次启动都以只读方式从该 CC Switch SQLite 数据库读取 `settings.claude_desktop_gateway_token`，使轮换后的令牌直接生效。数据库不可读、令牌缺失或空白时拒绝启动，不回退到桌面旧凭据，也不会创建或修改数据库。凭据仅注入子进程。路由或模型映射变化时先重新核对，不擅自切换提供商或修改 Codex 模型配置。

`doctor` 校验配置、路径、路由和模型映射，启用自动发现时还执行 `--version`，不发起模型请求，不能证明当前认证有效；真实认证在 `run` 时才暴露。上游 401 可能触发执行器内部重试，在外层表现为超时，需读取证据区分，不能只按普通网络超时处理。

`run` 返回 `ok: true` 且任务状态为 `pending_review`，表示本次执行器正常结束、结果等待 Codex 复核；`interrupted` 表示失败、超时或中断，需要读证据核查文件。结果正文在返回的 `evidence` 文件中。执行器成功不等于需求验收通过。路由校验失败时不会启动执行器，拒绝原因写入任务目录的 `执行拒绝-*.json` 并记录 `execution_rejected` 事件，任务负责人和状态保持不变。

`run` 的执行进程树随运行结束或控制进程退出而关闭；需要持续运行的服务应另外启动并交接，不作为本次派活的后台遗留进程。

Codex 接回后独立读改动和运行适当测试。需要返工时写明确检查点再派活；同一问题最多自动返工两轮，仍失败则向用户说明阻塞。执行器不能凭自己的声明完成最终审核。

## 终端看板

用户配置中设置 `terminal: true` 后，`run` 自动打开独立终端，持续显示任务目标与验收、Claude 操作与结果、Codex 复核及返工记录。将现有网页使用方式改成终端时，启用此项并将 `dashboard` 设为 `false`。同时启用两项时终端优先。返回 JSON 和执行证据包含 `terminal_pid`、`terminal_error`，开窗失败会反馈错误并继续派活。

手动在独立窗口查看使用 `monitor --task <ID> --open`，返回就绪进程的 PID。在当前终端跟随使用 `monitor --task <ID>`，读取一次使用 `monitor --task <ID> --once`。`--interval 1` 设置刷新秒数。当前终端的输出为中文滚动日志，`--open` 返回 JSON。关闭窗口或按 Ctrl+C 退出查看。

视图复用本地 SQLite 只读状态和脱敏 live JSONL。终端进程独立于执行器进程树，关闭视图时 Claude 继续运行。派活结束后窗口继续跟随 Codex 的复核和返工。相邻回复增量持续追加，完整回复到达时合并显示。长工具输出附有原日志路径，历史审核可用完整 `handoff` 追溯。查看及刷新由本地规则完成，不额外调用模型。

## 浏览器看板

需要在本机浏览器同一页面查看派活目标与验收、Claude 实时操作与日志、任务阶段、Codex 复核与返工记录时，运行：

`dashboard --task <ID> --no-open`（或去掉 `--no-open` 直接打开浏览器）。命令启动或复用当前项目的后台只读服务，返回 `url`、`pid`、`port`、`token` 等 JSON；`--port 0` 自动分配端口，服务只绑定 `127.0.0.1`。停止本项目的看板服务使用 `dashboard --stop`；关闭浏览器不会停止 Claude。

看板只读取项目已有 SQLite（只读模式）和 `协作记录/<task>/live-*.jsonl`，没有网页派活、暂停、终止或审批入口。URL 带随机能力 token，只接受本机 Host/Origin，静态资源为固定白名单。服务独立于单次派活的 Windows Job Object，日志集中在 `协作记录/看板/`，启动时不继承执行器注入的模型 token 环境，也不读取模型配置。读取既有 live 文件时先忽略 `system/thinking_tokens` 统计噪声再决定最近 5000 条窗口，不改写证据原件；页面对相邻文本增量合并显示，不展示 thinking，也不为每个增量单独占行。单次执行超过 5000 条有效事件时保留最近窗口并继续追加新事件，保留滚动和展开状态。摘要均由本地规则派生，不需要额外模型总结。

用户配置中 `dashboard` 为 `true` 时，`run` 会自动启动或复用看板、打开对应任务，并在结果中返回 `dashboard_url`；未配置或为 `false` 时不启动。配置默认关闭，测试与模拟执行器不启用自动打开。看板启动失败会写入 `dashboard_error`，不会返回不可用的 URL。

## Codex 额度不足

Claude 可在桌面 Local Code 选择同一项目，读取本 Skill 并接管；直接自行澄清、规划、实现和测试，不等待 Codex、不调用 `run` 自我委派。新决策和修改保持待 Codex 复核。

每完成一个实际阶段，将“目标与约束、已完成、实际验证、未验证和下一步”写入任务问题目录的检查点文件，运行 `checkpoint --task <ID> --agent claude --file '检查点绝对路径'`。Codex 保存自己的阶段时改用 `--agent codex`。完成阶段时也按现有共享记忆技能追加摘要；记录库不代替代码同步。

`checkpoint` 保存的阶段结果进入 `pending_review`，只表示“等待 Codex 复核的阶段结果”；执行仍在进行时保持 `running`。checkpoint 不能证明执行调用成功，真实执行是否成功以 `run` 返回的 `ok` 和 `evidence` 为准。

保存应在每个阶段完成时发生，不依赖额度耗尽通知。突然退出只能恢复到最近成功保存的文件和检查点。`takeover` 会识别已退出的控制/执行进程并记录中断；仍有子进程时拒绝接管。

## 最终审核与基线

只有实际 Codex 完成独立审核后，接管为 codex，保存审核意见，再对干净的代码提交运行：

`approve --task <ID> --agent codex --revision <完整HEAD> --report '审核意见绝对路径'`

该命令记录审核证据和基线，不证明调用者身份；两端须按真实角色操作。批准前要求任务起点和 `review_from` 都属于当前 HEAD 历史；历史重写或回退到任务起点之前时明确拒绝，须人工核对。未提交代码可以给出审核意见，但提交基线保持待固定；无 Git 目录仍可交接，不能宣称有提交基线。下次审核从 `review_from` 以及未提交、未跟踪代码开始核对。不会自动 push、merge 或部署。

## 运行位置变化

为适配桌面升级，可在配置中设置 `claude_code_root`，值为 Claude 桌面 `claude-code` 安装根目录的绝对路径。每次 `doctor` 和 `run` 在校验路由与认证来源后，按数字版本号、同版本文件更新时间选择 `<版本>/<构建>/claude.exe`，通过有超时的 `--version` 校验后使用，保留 `command` 的前置参数。空文件和校验失败的候选会跳过，全部不可用时明确报错。发现结果仅用于本次运行，配置文件保持原值；省略此字段时沿用固定 `command`。安装根目录迁移时需更新该字段。

两端使用同一份实际技能源；移动前更新目录链接和说明。新会话显式使用 `$project-relay` / `/project-relay` 最可靠，自动选择由宿主决定。自动派活的进程保护仅支持 Windows；运行前需取得当前用户对模型调用及其费用的授权。
